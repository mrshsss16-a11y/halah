# حزمة جاهزية تقديم تطبيق هالة إلى سلة

**الحالة:** جاهزة للتحضير الداخلي فقط، **وليست طلب تقديم أو تطبيقاً مسجلاً**.  
**البيئة المستهدفة عند التنفيذ لاحقاً:** staging مستقلة مع متجر demo.  
**حالة الإنتاج:** لا تغيير؛ لا OAuth، ولا webhook، ولا scope، ولا secret، ولا اتصال متجر، ولا نشر.

> لا تُنفّذ أي خانة تشغيلية في هذه الوثيقة إلا بعد موافقة صريحة منفصلة على إنشاء التطبيق أو تغيير إعداداته داخل Salla Partners.

## 1. تعريف التطبيق المقترح

هالة هي **نظام قرار محكوم للمتاجر**. تساعد التاجر على تنظيم facts المنتجات ومراجعة أدلتها قبل إنشاء drafts، كما تحاكي قرار استرداد السلات عبر سياسة وموافقة وقائمة إيقاف وسقف تشغيلي وقالب معتمد. لا تقدم هالة نفسها كبوت واتساب عام أو CRM مفتوح، ولا تسمح للنموذج بتجاوز مصدر الحقيقة أو قرار السياسة.

| الحقل في Salla Partners | الاقتراح الداخلي                                                               | حالة الجاهزية                         |
| ----------------------- | ------------------------------------------------------------------------------ | ------------------------------------- |
| الاسم العربي            | هالة                                                                           | يحتاج تأكيد المالك قبل إدخاله خارجياً |
| الاسم الإنجليزي         | Hala AI OS                                                                     | يحتاج تأكيد المالك قبل إدخاله خارجياً |
| النوع                   | Public App مقترح إذا كان الهدف الظهور في Marketplace؛ وإلا Private pilot أولاً | قرار تجاري معلق                       |
| الفئة                   | General App                                                                    | مقترح                                 |
| الوصف المختصر           | نظام قرار محكوم لمحتوى المنتجات واسترداد السلات                                | جاهز للتحرير النهائي                  |
| الموقع                  | صفحة هالة العامة؛ يراجع الرابط وسياسة الخصوصية قبل التقديم                     | غير معتمد للتقديم بعد                 |
| بريد الدعم              | عنوان دعم نطاق هالة مخصص، لا بريد شخصي                                         | غير متوفر بعد                         |
| الأيقونة                | أصل مربع مستقل بهوية هالة، لا يقل عن 250×250                                   | مطلوب من الهوية البصرية               |

توثق سلة أن إنشاء التطبيق يتطلب حساب Partners موثقاً، وأن بيانات التطبيق الأساسية تشمل الأيقونة والاسم بالعربية والإنجليزية والفئة والوصف المختصر والموقع وبريد الدعم.[1] كما تفرق بين التطبيق العام والخاص؛ لا يعني هذا الاختيار إنشاء أي تطبيق في الوقت الحالي.[1]

## 2. ما سيطلب من التاجر وما لن يطلب

يركز التطبيق على أقل وصول ممكن. محتوى المنتجات يبقى draft-first، ولا يكتب إلى المتجر في المرحلة الأولى. استرداد السلات لا يرسل شيئاً عند وصول حدث؛ إذ يمر الحدث لاحقاً عبر التحقق والتكرار والسياسة والموافقة والقائمة والسقف والقالب قبل الجدولة.

| الوظيفة                            | الوصول المقترح                                              | قرار النطاق                                                       |
| ---------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| معلومات هوية التطبيق وتفويض المتجر | `offline_access` عند الحاجة إلى تجديد مخول                  | مطلوب فقط في مرحلة OAuth المؤكدة                                  |
| إدارة اشتراكات webhook             | `webhooks.read_write`                                       | لا يطلب قبل جاهزية endpoint والتحقق في staging                    |
| قراءة أو تحديث منتجات              | `products.read_write`                                       | مؤجل؛ لا يستخدم إلا بعد preview واعتماد صريح وتحقق من عقد التصدير |
| استرداد سلات                       | نطاق الحدث/القراءة المناسب الذي تؤكده وثائق سلة وقت التقديم | غير محسوم؛ لا يطلب تخميناً                                        |
| عملاء أو طلبات أو مدفوعات          | لا يطلب كصلاحية عامة                                        | ممنوع حالياً؛ لا يضاف إلا بضرورة مثبتة ومراجعة خصوصية             |

توثق سلة أن `webhooks.read_write` مطلوب لتسجيل webhook، وأن تسجيل الاشتراك يتطلب URL يستقبل `POST`، مع webhooks جديدة بالإصدار 2 افتراضياً.[4] وتوضح وثائق OAuth أن scopes تحدد الوصول، وأن `state` جزء من تدفق التفويض للحماية من CSRF.[2]

## 3. تصميم OAuth المقترح قبل التنفيذ

للتطبيق المنشور، تذكر وثائق سلة أن **Easy Mode** هو المسار المسموح للتطبيقات المنشورة في App Store؛ أما Custom Mode فيبقى للاختبار أو الحالات المتقدمة وفق ما تؤكده الوثائق عند التنفيذ.[2] القرار النهائي لا يُثبت هنا قبل فتح التطبيق في Partners ومراجعة متطلبات النشر الحالية.

| العنصر        | تصميم هالة المطلوب                                        | الحالة الآن |
| ------------- | --------------------------------------------------------- | ----------- |
| بيئة الربط    | `staging` مستقلة مع متجر demo فقط                         | غير منشأة   |
| OAuth state   | عشوائي لمرة واحدة، مخزن كـhash بمدة قصيرة ومرتبط بالمنظمة | غير منفذ    |
| callback      | خادمي فقط؛ يفحص state قبل التعامل مع code                 | غير منفذ    |
| tokens        | تشفير خادمي، خارج المتصفح والسجلات وGit                   | غير منفذ    |
| refresh       | قفل/معاملة لكل اتصال لمنع إعادة استخدام refresh token     | غير منفذ    |
| إلغاء الاتصال | يحول الاتصال إلى حالة نهائية ويوقف المعالجة               | غير منفذ    |

توضح سلة أن access token محدود المدة وأن refresh token أحادي الاستخدام؛ إعادة استخدامه بالتوازي قد تبطل التفويض، لذلك يلزم قفل أو معاملة مخصصة قبل إدخال OAuth في staging.[2]

## 4. تصميم webhook المقترح قبل التنفيذ

لن تسجل هالة أي webhook الآن. بعد بناء endpoint واختباره، يكون المسار المقترح كما يلي:

```text
POST /webhooks/salla
  → rate limit مبكر
  → قراءة raw body مرة واحدة
  → تحقق من strategy والتوقيع بمقارنة ثابتة الزمن
  → parse بعد نجاح التحقق فقط
  → حفظ inbox/idempotency في D1
  → 2xx سريع
  → workflow منفصل: policy → consent → suppression → budget → template
```

> وصول حدث `abandoned.cart` لا يساوي إذناً للإرسال. لا تصل أي حالة إلى إرسال إلا بعد كل البوابات المذكورة، ولا يستخدم النموذج اللغوي لاتخاذ قرار القناة أو السياسة.

تسرد وثائق سلة استراتيجية Signature ورؤوس التحقق ذات الصلة، وتشدد على رفض الطلبات غير الموثوقة.[3] وتذكر كذلك أن مزود الويب هوك يعيد المحاولة عند غياب الاستجابة الناجحة، لذا يجب أن يكون الاستقبال سريعاً وقابلاً للتكرار.[3] لا تسجل هالة الجسم الخام أو التوقيع أو token في السجلات التطبيقية.

## 5. خطة demo المطلوبة للتقديم

لا تستخدم هذه الخطة متجر عميل أو رقماً حقيقياً. يجري الاختبار في متجر demo، كما توصي وثائق سلة لمسار اختبار التطبيق.[1] [2]

| السيناريو                              | دليل القبول                                                    | مخرج هالة المتوقع                   |
| -------------------------------------- | -------------------------------------------------------------- | ----------------------------------- |
| تثبيت التطبيق في متجر demo             | نجاح التفويض بدون ظهور token في المتصفح أو السجل               | اتصال staging مشفر ومنظمة واحدة     |
| حدث توقيع صحيح                         | إدخال inbox واحد فقط                                           | معالجة مؤجلة بلا رسالة              |
| توقيع خاطئ أو body معدل                | 401/رفض آمن                                                    | لا كتابة أثر عمل                    |
| حدث مكرر                               | لا حالة أو إرسال مكرر                                          | idempotency محفوظة                  |
| سلة مكتملة أو جهة موقوفة أو بلا موافقة | reason code قابل للشرح                                         | `suppressed` أو تصعيد، لا إرسال     |
| قالب غير معتمد أو ميزانية غير متاحة    | قرار منع صريح                                                  | لا جدولة ولا رسالة                  |
| تفعيل محتوى المنتجات                   | 20 SKU تركيبية أو demo تمر import → evidence → draft → preview | لا export إلى متجر قبل اعتماد منفصل |

## 7. بوابات لا تقبل التجاوز قبل التقديم

لا تنتقل هالة من هذه الحزمة إلى تقديم فعلي حتى يتحقق كل بند في الجدول التالي.

| البوابة             | المعيار                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| Security            | تمر اختبارات OAuth state، التشفير، raw-body HMAC، idempotency، وسباق refresh token في staging. |
| Environments        | موارد D1/KV/سر staging مستقلة؛ لا binding أو secret إنتاجي في development أو staging.          |
| Product safety      | لا إرسال واتساب من webhook، ولا نموذج يقرر eligibility، ولا export محتوى بلا preview واعتماد.  |
| Privacy             | سياسة خصوصية وشروط استخدام ومصفوفة احتفاظ وحذف ومراجعة مختصة.                                  |
| Demo                | متجر demo، endpoint staging مستقر، rollback واختبارات توقيع وتكرار ومنع.                       |
| Operations          | مراقبة آمنة، alerting، kill switch، سجل تدقيق، playbook دعم، وخطة إلغاء اتصال.                 |
| Submission evidence | الأيقونة والأوصاف ولقطات الشاشة والفيديو وبريد الدعم والروابط المعتمدة مكتملة.                 |

## 8. تفويض مطلوب قبل أي خطوة خارجية

عند اكتمال الحزمة، ستطلب هالة تأكيداً منفصلاً ومحدداً يذكر العملية والبيئة. أمثلة ذلك: «أنشئ تطبيقاً جديداً في Salla Partners»، أو «سجل redirect URL في staging»، أو «ارسل طلب النشر». لا تكفي هذه الوثيقة أو رغبة عامة في التقديم لتفويض أي واحد من تلك الأفعال.
