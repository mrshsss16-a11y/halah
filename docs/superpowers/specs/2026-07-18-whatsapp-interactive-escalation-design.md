# تصميم: أزرار حجز تفاعلية + تصعيد تلقائي للإنسان (رقم أورا)

تاريخ: 2026-07-18

## النطاق

محصور برقم أورا فقط (`merchantId === "hala"` بـ`functions/api/whatsapp/webhook.js`). لا تغيير على منتج التاجر (`PERSONA_SYSTEM_PROMPT`، متاجر Salla/Trendyol).

## المشكلة

1. حجز الاستشارة يعتمد على الموديل يكتب `[BOOK_SLOT:النص]` بالضبط، ويستخرجه الكود بـregex — هش، أي انحراف بصياغة الموديل يفشل الحجز صامتاً.
2. لا آلية تصعيد لإنسان لما يعجز البوت أو يكون الطلب معقد — يستمر يحاول يرد بلا نهاية حتى لو ما يعرف الجواب.

## الحل

### ١. قائمة حجز تفاعلية حقيقية (WhatsApp List Message)

- الموديل يكتب ماركر نية بسيط `[OFFER_SLOTS]` (بدل تنسيق الفتحات يدوياً).
- الكود (مو الموديل) يستبدل الماركر بإرسال **List Message** حقيقية — فتحات `WEEKLY_SLOTS` كخيارات ضغط (حتى ١٠ صفوف، الحد الأقصى المسموح).
- العميل يضغط فتحة → يرجع webhook بنوع `interactive` (`list_reply.id`/`title`) → الكود يسجل الحجز **مباشرة بدون أي تخمين نصي**، يرسل رسالة تأكيد.
- المسار النصي القديم (لو العميل كتب الفتحة يدوياً بدل الضغط) يبقى كـfallback — نفس regex الحالي، ما نحذفه.

### ٢. تصعيد تلقائي للإنسان

**مسارين للتصعيد — الموديل يقرر، أو الكود يتدخل كشبكة أمان:**

**أ. تصعيد بقرار الموديل:** يكتب ماركر `[ESCALATE]` لما يحس إنه ما يقدر يجاوب (لا معرفة RAG ذات صلة + السؤال خارج نطاق `HALA_SUPPORT_PROMPT`) أو الطلب معقد (شكوى، تفاوض سعر، تفصيل تقني عميق).

**ب. شبكة أمان بالكود (بدون اعتماد على الموديل):** لو نفس الرقم رسل **٣ رسائل متتالية بآخر ساعة** بدون ما يصير حجز أو تصعيد بينهم — الكود يصعّد تلقائياً، بغض النظر عن قرار الموديل. يمنع "البوت يلف بدائرة" مع عميل محبط.

**عند أي تصعيد (أ أو ب):**
- رد للعميل: "حولت طلبك لفريقنا، بيردون عليك قريب 🙌" (نص ثابت بالكود، مو الموديل — يضمن رد متسق).
- تسجيل outbound بمصدر `source='escalated'`.
- البوت يسكت تلقائياً على هالمحادثة بالذات — **نفس آلية سكوت الساعتين الموجودة أصلاً**، لأن أورا يشوف كل رسالة بجواله عبر Coexistence، صفر حاجة لقناة تنبيه منفصلة.

## تغييرات الكود بالتفصيل

| الملف | التغيير |
|---|---|
| `functions/_lib/whatsapp.js` | دالة جديدة `sendWaInteractiveList(env, {to, bodyText, buttonText, rows})`. `parseInbound()` يدعم نوع `interactive` (`list_reply.id`/`title`) بجانب `text`. |
| `functions/_lib/persona.js` | `BOOKING_INSTRUCTIONS` تتحدث لماركر `[OFFER_SLOTS]` فقط (تشيل تنسيق الفتحات اليدوي). إضافة تعليمات `[ESCALATE]` لـ`HALA_SUPPORT_PROMPT`. |
| `functions/_lib/db.js` | `getLastHumanReplyAt` يتحقق `source IN ('human','escalated')` بدل `= 'human'` بس (إعادة استخدام، صفر دالة جديدة). دالة جديدة `countRecentInboundWithoutResolution(env, merchantId, phone, sinceMinutes=60)` لعدّاد شبكة الأمان. |
| `functions/api/whatsapp/webhook.js` | كشف `[OFFER_SLOTS]` → إرسال List Message بدل رد نصي. كشف `interactive.list_reply` → تسجيل حجز مباشر. كشف `[ESCALATE]` أو شبكة الأمان (٣ رسائل/ساعة) → رد التحويل الثابت + `source='escalated'`. |

## قيود الحفاظ

- صفر تغيير على `chat.js`/`copy.js`/تدفقات التاجر.
- المسار النصي الحالي لكل من الحجز والرد يبقى شغال كـfallback — إضافة، مو استبدال.
- لا رسالة تحويل بصياغة حرة من الموديل — نص ثابت بالكود لضمان الاتساق.

## الاختبار

- فحص حي: عرض حجز → رسالة List حقيقية تصل → ضغط فتحة → حجز يسجل بـD1 فوراً بدون خطأ تنسيق.
- فحص شبكة الأمان: ٣ رسائل متتالية بدون رد حاسم → تصعيد تلقائي حتى لو الموديل ما كتب `[ESCALATE]`.
- تأكيد: البوت يسكت على المحادثة المصعّدة بس، باقي العملاء ما يتأثرون (نفس فحص السكوت السابق).
- `node --check` على كل ملف معدّل + `npm run stage` قبل كل commit.
