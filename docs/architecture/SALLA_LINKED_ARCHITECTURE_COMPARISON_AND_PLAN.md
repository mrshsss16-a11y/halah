# مقارنة بنية `halah.aura.sa` المرتبطة بسلة مع المصدر الجديد وخطة سد الفجوات

**التاريخ:** 2026-09-01  
**النطاق:** مقارنة قراءة فقط، ثم خطة تنفيذ مقترحة.  
**القرار المحوري:** `halah.aura.sa` هو المرجع التشغيلي الحالي المرتبط بتطبيق سلة، بينما مستودع `mrshsss16-a11y/halah` هو المرشح الأفضل ليكون نواة SaaS النهائية بعد إكمال عقود Salla والإنتاج.

## 1. الحكم التنفيذي

البنية الموجودة خلف `halah.aura.sa` هي **الأكثر جاهزية من ناحية الارتباط الحالي بسلة**؛ فهي مشروع Cloudflare Pages قائم باسم `hala-ai-os` وله نطاق alias هو `halah.aura.sa`، كما أن إعداداته تحتوي على موارد D1 وKV وVectorize وWorkers AI وأسماء أسرار مرتبطة بسلة وGoogle وWhatsApp. لكن هذا يثبت وجود التكاملات في إعدادات البيئة فقط، ولا يثبت أن كل التدفقات تعمل أو أن الأسرار الحالية صالحة أو أن الكود قابل للصيانة.

المصدر الجديد هو **الأكثر جاهزية من الناحية الهندسية والأمنية**. يحتوي على عزل المؤسسات، جلسات hashed، أدوار وصلاحيات، حماية CSRF وCSP، خزانة رموز مشفرة، سياسات الاسترداد، دورة محتوى المنتجات، واختبارات وحدة وعقود وتكامل. لكنه ما زال يقدّم Salla كتدفق mock محلي محمي ببيئة development، وليس كـOAuth حي لتطبيق سلة منشور.

لذلك القرار الصحيح ليس نسخ المشروع القديم إلى الجديد، ولا نشر الجديد فوق قاعدة القديم. القرار الصحيح هو أن تصبح البنية الجديدة **الـruntime الأساسي**، وأن تُنقل إليها العقود المؤكدة من تجربة `halah.aura.sa`، مع إبقاء Pages القديم سليماً حتى ينجح cutover قابل للرجوع.

## 5. خطة الإضافة والنقل

### المرحلة A: تثبيت عقد سلة قبل أي cutover

يُنشأ أولاً جدول توافق بين المسارات التي يعرفها تطبيق سلة والمسارات التي سيقدمها Worker الجديد. يجب تثبيت `redirect_uri` وwebhook URL وscope المطلوبة ونسخة event envelope. لا تُعتبر `/salla/mock/start` أو `/salla/mock/complete` بديلاً عن Easy Mode أو OAuth لتطبيق منشور؛ وضع OAuth الصحيح يعتمد على حالة نشر التطبيق في Salla [2].

بعد ذلك يُنفذ adapter Salla داخل `adapters/`، بينما تبقى state وpolicy والـauthorization في طبقاتها الحالية. يظل `client_secret` على الخادم فقط، ويُحفظ access/refresh token داخل Vault المشفر. عند تدوير refresh token يجب استخدام lease أو transaction حتى لا تستعمل طلبات متوازية الرمز القديم مرتين [2].

**معيار خروج المرحلة:** اختبارات contract تغطي success وinvalid state وexpired state وinvalid code و401 و429، إضافة إلى متجر demo مع عدم تسجيل أي webhook أو إرسال حقيقي إلى متجر عميل.

### المرحلة B: تجهيز runtime إنتاج مستقل

يُنشأ Worker إنتاج باسم مستقل، مع D1 إنتاج جديد وKV إنتاج جديد. تطبق migrations الخمس عشرة على D1 الجديد فقط. لا يُستخدم `halah-tr-db` لأن schema legacy مثبتة ومختلفة، ولا يُستخدم `HALA_CACHE` لأن ذلك قد يخلط cache أو rate limits بين نظامين.

يجب أن تكون bindings الإنتاجية صريحة: `DB` إلى D1 الجديد، و`AUTH_RATE_LIMIT` إلى KV الجديد، وأي `VECTORIZE_INDEX` أو `AI` يُضاف فقط بعد اختبار الحاجة الفعلية وتحديد مصدر المعرفة. الأسرار تُدخل كـsecret bindings مستقلة ولا تظهر في config أو commit أو logs.

**معيار خروج المرحلة:** build production dry-run، migrations نظيفة، فحص schema، smoke test للـhealth وlogin وlogout، وفشل آمن عند غياب secret حرج.

### المرحلة C: إكمال Google Login والدخول التجاري

يوجد خياران مقبولان. الخيار الأول تنفيذ Google OAuth من الخادم مع state وnonce وربط الحساب بهوية منظمة، مع منع إنشاء حسابات مكررة. الخيار الثاني إخفاء Google مؤقتاً والإبقاء على البريد وكلمة المرور حتى يكتمل التدفق. الخيار غير المقبول هو عرض زر Google يعمل جزئياً أو يعتمد على إعداد قديم غير مثبت.

في المرحلة نفسها تُضاف email verification وpassword reset بواسطة adapter للبريد، مع رموز hash-only وTTL وإبطال بعد الاستخدام، وبلا إرسال فعلي أثناء الاختبارات إلا إلى صندوق اختبار معزول.

### المرحلة D: تحويل الوعود التسويقية إلى وظائف قابلة للإثبات

تُنقل من تجربة `halah.aura.sa` الرحلة المفهومية فقط: تسجيل، إضافة متجر، تجهيز بيانات المحتوى، ضبط سياسة الاسترداد، ثم عرض حالة التفعيل. لا تُنقل ادعاءات مثل «مجاني 100%» أو نسب التحسن أو وعود زمنية ما لم توجد بيانات معتمدة. كل خدمة عملاء يجب أن تعتمد على policy فعالة في D1، وكل استرداد لسلة يجب أن يمر عبر consent وsuppression وeligibility.

### المرحلة E: تفعيل السلة المتروكة وWhatsApp بعد ثبات الربط

بعد نجاح OAuth وwebhook، يُضاف مسار event workflow منفصل: استقبال raw body، HMAC، inbox، idempotency، ثم معالجة لاحقة. لا يُستدعى LLM أو WhatsApp داخل webhook handler. يمر الحدث بآلة الحالات `received → deduplicated → policy_checked → eligible → scheduled → sent|suppressed|escalated|failed`.

تُضاف قناة WhatsApp كـadapter لا كمنطق داخل UI، مع opt-in، قاطع تكلفة، حدود retry، templates معتمدة، وسجل تدقيق. الاختبار الأول mock transport فقط، ثم sandbox إن توفر، ولا يرسل إلى رقم أو متجر حقيقي دون موافقة مستقلة.

### المرحلة F: cutover النطاق

بعد اجتياز المراحل السابقة يُنشر Worker على hostname مؤقت أو route داخلي، ويُنفذ smoke كامل قبل ربط النطاق. تبقى Pages القديمة وD1 legacy دون حذف. عند نجاح الفحص، يُحوّل `halah.aura.sa` إلى Worker الجديد عبر إعداد Cloudflare المناسب، ثم يُفحص login وSalla callback وwebhook وواجهات RTL والـsecurity headers.

إذا فشل أي فحص حرج، يُعاد النطاق إلى Pages القديم أو يُعطل route الجديد، دون حذف الموارد الجديدة أو لمس قاعدة legacy. لا يُعتبر حذف المشروع القديم جزءاً من cutover الأول.

## 7. ما لا ينبغي فعله

لا ينبغي نشر المصدر الجديد فوق مشروع Pages القديم لمجرد أن النطاق نفسه صحيح. ولا ينبغي ربطه بـ`halah-tr-db` أو `HALA_CACHE`. كما لا ينبغي اعتبار أسماء الأسرار القديمة دليلاً على أن Google أو Salla أو WhatsApp تعمل، ولا ينبغي تسجيل webhook إنتاجي أو استخدام token حقيقي قبل إكمال عقد OAuth والاختبارات.

كذلك لا ينبغي نسخ وظائف غير مرئية من المشروع القديم بالتخمين. ما يمكن نقله الآن هو تجربة المستخدم والوظائف التي أثبتها الكود الجديد؛ أما منطق Pages Functions أو محتوى Vectorize أو بيانات D1 القديمة فيحتاج مصدراً فعلياً أو إعادة بناء اختبارية.

## 8. معيار الجاهزية النهائي

يُعتبر المنتج جاهزاً للبيع عندما ينجح الربط الحي مع متجر Salla demo، وتُحفظ الرموز مشفرة، وتُرفض إعادة استخدام state، ويصل webhook إلى inbox دون تكرار، وتعمل آلة الحالة والسياسات، ولا توجد إجابة خدمة عملاء بلا evidence فعال، ولا توجد رسالة WhatsApp بلا consent، وتعمل رحلة التسجيل والدخول والاسترداد، وتنجح اختبارات العزل بين منظمتين، ويكون هناك rollback مثبت دون حذف Pages القديم.

**الخلاصة:** القديم هو الأكثر جاهزية للاتصال الحالي بسلة، والجديد هو الأكثر جاهزية ليكون المنتج النهائي. الإضافة الصحيحة ليست نقل قاعدة القديم، بل نقل عقود Salla والرحلة التجارية إلى بنية الجديد ثم تحويل النطاق بعد إثبات التوافق.
