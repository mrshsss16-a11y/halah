# حالة تنفيذ المصدر الجديد لهالة

**البيئة المنفذة:** development محلية ومعزولة.  
**تاريخ التحديث:** 24 أغسطس 2026.
**حالة الإنتاج:** لم يتغير. لا نشر، ولا تعديل Cloudflare، ولا تسجيل webhook، ولا OAuth، ولا أسرار، ولا متجر أو عميل أو رقم WhatsApp حقيقي.

> لا تمثل هذه النتيجة إطلاقاً أو جاهزية production. تمثل **Commercial Local MVP Alpha** قابلاً للعرض الداخلي والاختبار ببيانات تركيبية فقط.

## ما بقي قبل أول staging

لا تزال هذه الخطوات مقصودة وغير منفذة: قرار export فعلي مستقل إلى بيئة staging بعد المراجعة وسجل التسليم/rollback له، email verification/reset password، namespace KV مستقلة لـstaging/production وتحقق load/concurrency، OAuth سلة وstate store والتشفير، raw webhook route وHMAC وفق عقد سلة، WhatsApp transport وdelivery callbacks، ModelRouter وتوليد drafts/vision مع budget/circuit breakers، Playwright/axe وRed Team، موارد staging مستقلة، ومتجر demo وWhatsApp sandbox.

> لا تدل نتيجة build الجاف أو mock على أن سلة أو Meta جاهزان. الاتصال الفعلي يحتاج عقداً رسمياً، sandbox أو متجر demo، وفحصاً أمنياً، وموافقة منفصلة قبل إنشاء مورد أو تسجيل callback أو استخدام أسرار.

## تحقق واجهة النسخة التجارية (محلي فقط)

- فُتحت الصفحة العامة على `http://localhost:8787/` بنجاح: العنوان عربي و`dir="rtl"` ظاهر، ومسارات الدخول وإنشاء مساحة المتجر متاحة.
- فُتح نموذج `/signup` بنجاح: يطلب اسم مساحة المتجر والبريد وكلمة مرور، ويصرح أنه لا يربط متجراً أو قناة في هذه المرحلة.
- لم تُدخل بيانات حقيقية ولم يُجرَ اتصال بأي خدمة خارج البيئة المحلية أثناء هذا التحقق.
- اكتملت رحلة اختبار تركيبية: إنشاء منظمة باسم اختبار، إنشاء جلسة محلية، والانتقال إلى `/app` بنجاح. عرضت اللوحة حالات البداية «غير مربوط»، «لم يبدأ»، و«غير مهيأ» بوضوح، ولم تُستخدم أي بيانات أو قناة أو متجر حقيقي.
- تحقق محلي إضافي: استمرّت الجلسة التجريبية بعد إضافة حارس الأصل، ونجح إرسال طلب تفعيل تركيبي من `/app/activation` إلى D1 المحلية؛ ظهرت رسالة الاستلام ولم يحدث أي اتصال بسلة أو Meta أو Cloudflare أو أي خدمة خارجية.
- أُضيف حارس أصل موحّد للعمليات المتغيرة للحالة في التسجيل والدخول والخروج وطلب التفعيل. تقبل الواجهة الطلبات من أصلها فقط، مع كوكي `HttpOnly; SameSite=Lax` موجودة مسبقاً؛ يبقى CSRF token المتقدم مطلباً قبل staging متعدد المستخدمين.
- اكتمل اختبار محلي لمسار محتوى المنتجات: قُبل صف facts تركيبي بسجل SKU ومصدر `https`، وحُفظ في D1 المحلية بحالة `ready_for_generation`. لا يشغّل هذا المسار نموذجاً، ولا ينشئ وصفاً، ولا يصدّر أو ينشر إلى متجر. لاحقاً شُدّدت بوابة الدليل: وجود رابط `https` لا يعد اعتماداً؛ فالدفعات الجديدة تبقى في `needs_evidence` وتعرض للمراجع رسالة اعتماد صريحة قبل أي توليد. اختُبر الاعتماد ببيانات تركيبية: انتقل `SKU-BRAVO` إلى `approved`، وتحولت الدفعة إلى `ready_for_generation`، وسُجل حدث `product_fact_evidence_approved` في `audit_events` المحلية؛ وهذه الحالة ما زالت لا تستدعي نموذجاً أو تصديراً أو نشرًا.
- اكتمل تحقق محلي لمحاكاة الاسترداد: مع غياب موافقة القناة أعادت البوابة `missing_consent` ورسالة منع صريحة. المحاكاة لا تستقبل webhook ولا تحفظ سلة أو جهة اتصال ولا تنشئ رسالة أو محاولة إرسال.
- أُغلقت فجوة عزل جلسة متعددة المنظمات: تضيف migration `0004_session_organization_scope.sql` نطاق `organization_id` إلى كل جلسة، وتتحقق القراءة من العضوية والمنظمة النشطتين. اختبر Worker/D1 محلياً أن جلسة مرتبطة بالمنظمة ب لا تعود إلى أول عضوية للمستخدم في المنظمة أ، وأن حذف العضوية المرتبطة يجعل الجلسة غير صالحة. لا تستخدم الاختبارات أي D1 أو Cloudflare بعيد.
- أُضيف حارس KV محلي للمصادقة: يسمح بعدد محدود من محاولات التسجيل أو الدخول ضمن نافذة قصيرة، ويخزن مفتاحاً مشتقاً مجزأً من البريد وعنوان العميل بدلاً من القيم الخام. عند بلوغ الحد يعيد `429` و`Retry-After`، وعند تعذر KV يعيد `503` ولا يكمل المصادقة. binding التطويري اسمي ومحلي في `wrangler.jsonc`؛ لم يُنشأ KV أو secret في staging أو production.
- توسعت اختبارات D1/Worker المحلية لعزل لوحة التاجر: لا تظهر حالة الربط أو محتوى المنتجات أو سياسة الاسترداد أو طلب التفعيل للمنظمة أ داخل لوحة المنظمة ب، كما يبقى طلب تفعيل المنظمة ب منفصلاً عن حالة المنظمة أ. لا توجد أي بيانات متجر أو عميل أو تكامل شبكة في هذا الاختبار.
- اكتمل مسار مسودة يدوية محكوم محلياً: لا تقرأ الخدمة إلا facts ذات `evidence_status=approved` ضمن المنظمة، ثم تتحقق من ظهور كل claim في النص وارتباطه بمفتاح fact موجود وتمنع لغة العلاج أو الضمان غير المدعومة. تحفظ النتيجة `ready_for_review` أو `needs_revision` مع خريطة الأدلة وسجل تدقيق؛ لا يوجد نموذج أو preview أو export أو نشر. اختبرت الواجهة مسودة تركيبية وانتهت إلى `ready_for_review` وسجل تدقيق واحد في D1 المحلية فقط.
- أُضيف طابور مراجعة المسودات: يعرض فقط `ready_for_review` ضمن منظمة الجلسة ويطلب قراراً صريحاً باعتماد المعاينة أو الرفض مع ملاحظة. الاعتماد ينقل المسودة إلى `approved_for_preview` ويسجل المراجع والوقت والملاحظة وحدث تدقيق؛ لا ينشئ preview أو ملف تصدير أو تحديث متجر. اختبرت قرار اعتماد تركيبي محلياً واختفى العنصر من طابور المراجعة وسُجل حدث اعتماد واحد.
- أُضيفت معاينة داخلية تقرأ حصراً drafts ذات `approved_for_preview` في المنظمة نفسها وتعرض النص وخريطة الأدلة. ويتاح CSV محلي للمراجعة من نفس projection وبـSKU والمرجع وBOM للغة العربية؛ لا يحوّل التنزيل بيانات إلى سلة أو أي متجر ولا ينشئ قرار export أو تحديثاً. تغطي الاختبارات escaping CSV وحجب غير المسجلين، وتبقى عزل المنظمة مغطاة في D1/Worker.
- أُضيف سجل staging داخلي منفصل في migration `0007_product_content_export_staging.sql`: المالك فقط يستطيع اختيار مسودات `approved_for_preview` وتجميد لقطة JSON مرتبطة بـSKU والمرجع داخل D1، ثم تسجل العملية في `audit_events` بسبب `csv_review_local_only`. لا تغير العملية حالة المسودة ولا تنشئ ملفاً إضافياً ولا ترسل شيئاً إلى سلة أو أي متجر. اختبرت D1/Worker منع إدخال draft من منظمة أخرى بلا أي stage أو audit، ثم تحققت الواجهة محلياً ببيانات تركيبية من حفظ سجل واحد وظهور رسالة صريحة بعدم وجود تصدير أو تحديث متجر.
- أُضيف دور `reviewer` في migration `0011_content_reviewer_role.sql` محلياً فقط. يستطيع المالك أو المشغّل أو المراجع اعتماد evidence ومراجعة المسودات، بينما تبقى كتابة facts والمسودات للمشغّل/المالك وتجهيز سجل CSV الداخلي وإدارة الاتصال للمالك فقط. طبقت migration بنجاح على D1 المحلية. يثبت اختبار HTTP/D1 تكاملي بجلسة reviewer تركيبية أن اعتماد evidence ومراجعة المسودة ينجحان، وأن استيراد facts وتجهيز سجل CSV ومحاولة ربط سلة local mock تعيد حظراً قبل أي تغيير. لا توجد دعوات فريق أو تغيير أدوار عبر الواجهة بعد.
- أُصلح مسار واجهة المصادقة الذي اكتشفه فحص محلي: النماذج تستخدم الآن `POST` صريحاً إلى مسارات API، وتبقى CSP صارمة مع nonce عشوائي لكل طلب على السكربتات الداخلية بدلاً من السماح الشامل للسكربتات المضمنة. تحقق اختبار انحدار من عدم وجود action يعود إلى `/signup` أو `/login` ومن مطابقة nonce بين الرأس والـHTML. أُعيدت رحلة إنشاء منظمة تركيبية محلياً ووصلت إلى `/app` من دون كلمة مرور في العنوان، ثم تحققت صفحة محتوى المنتجات من اكتمال تحميلها الديناميكي تحت CSP nonce.
- أُضيف CSRF double-submit محلي فوق حارس الأصل: تصدر طلبات القراءة كوكي `hala_csrf` عشوائية ذات `SameSite=Strict` وخصائص `Secure` خارج development، ويجب أن يطابقها header `x-hala-csrf` بمقارنة ثابتة الزمن في كل عمليات المصادقة والمحتوى والتفعيل والاسترداد وlocal Salla mock. لا يمر webhook سلة بهذا الحارس لأنه يستخدم تحقق HMAC مستقلاً. تغطي الاختبارات غياب/اختلاف token، وأكد فحص المتصفح أن محاكاة الاسترداد تمر بالـtoken وتعيد قراراً محكوماً فقط بلا كتابة بيانات عميل أو إرسال.
- أُضيفت واجهة `/app/audit` وAPI قراءة فقط `/api/audit-events` لتعرض metadata لسجل المنظمة الحالية حصراً: action، الكيان، السبب، الوقت ومعرّف الطلب. تدعم API ترقيم صفحات محدوداً وفلتر action صارماً، ولا تعيد actor email أو secrets أو token أو جسم webhook أو بيانات عميل. تضيف migration `0012_audit_events_action_index.sql` فهرساً محلياً للاستعلام المفلتر. تحققت اختبارات D1 من العزل والفلترة والصفحات، وتحقق اختبار HTTP من ظهور أحداث reviewer نفسها ضمن منظمة الجلسة؛ فحص المتصفح واجهة الحالة الفارغة المتوقعة محلياً.
- رُقيت أداة البناء إلى `wrangler 4.125.0` وتعريفات Workers إلى `5.20260823.1`. ينجح build الجاف الآن تحت compatibility date المطلوب بلا تحذير fallback من Wrangler. بقي تحذير fallback في Miniflare لاختبارات التكامل بسبب الاعتماد الحالي `@cloudflare/vitest-pool-workers 0.8.x` المتوافق مع Vitest 3؛ الانتقال المدعوم إلى `@cloudflare/vitest-plugin`/Vitest 4 يحتاج migration اختبارات مستقلاً وموثقاً، لذا لا يزال بنداً صريحاً قبل اعتماد staging الكامل.
- أُضيفت دورة حياة فريق متجر محلية في migration `0013_organization_team_invitations.sql`: يعرض `/app/team` أعضاء المنظمة ودعواتها، ويستطيع المالك فقط إنشاء دعوة أو تعديل دور أو إزالة عضو. الدعوة hash-only في D1، قصيرة العمر وحالاتها `pending/accepted/revoked/expired`؛ تظهر raw token مرة واحدة في development فقط لاختبار محلي ولا ترسل بريداً أو تسجل في audit أو fixture. قبول الدعوة يطابق بريد الحساب المسجّل ويُنشئ عضوية ثم جلسة مقيّدة بالمنظمة المقبولة. تُبطل إزالة العضو جلساته في المنظمة، وتحمي D1 آخر owner من خفض دوره أو إزالته. تغطي الاختبارات D1 تخزين الدعوة والأثر التدقيقي والقبول والحماية وإبطال الجلسة، ويثبت اختبار HTTP أن reviewer لا يستطيع إنشاء دعوة حتى مع CSRF صحيح. لا يوجد إرسال بريد أو invitation delivery في staging/production قبل اعتماد مزود بريد.
