# خطة جاهزية Staging لهالة

**الوضع الحالي:** وثيقة تخطيط محلية فقط. لم تُنشأ موارد، ولم تُغير Cloudflare، ولم تُسجل URLs أو secrets أو webhooks.  
**الهدف:** تجهيز بيئة staging مستقلة لاختبار متجر Salla demo قبل أي اتصال بمتجر عميل أو قناة WhatsApp حقيقية.

## مبدأ العزل

تحتاج هالة إلى ثلاث بيئات منفصلة وظيفياً وبيانياً. لا يجوز أن يستخدم development أو staging أي binding أو secret أو D1 أو KV أو Vectorize من الإنتاج.

| البيئة      | الغرض                                                        | البيانات المسموح بها                   | المحظور                                              |
| ----------- | ------------------------------------------------------------ | -------------------------------------- | ---------------------------------------------------- |
| development | بناء واختبارات محلية                                         | fixtures تركيبية فقط                   | شبكة متجر، tokens، عملاء، أرقام، production bindings |
| staging     | تكامل contract مع متجر Salla demo وقناة اختبار معتمدة لاحقاً | بيانات demo ومخففة وموافق عليها        | متجر عميل، قائمة عملاء فعلية، إرسال تسويقي حي        |
| production  | خدمة تجارية معتمدة                                           | بيانات العميل الضرورية فقط وفق السياسة | تجارب غير مضبوطة أو keys مشتركة مع staging           |

## الموارد المقترحة

الأسماء أدناه **اصطلاحات اقتراحية فقط** وليست أوامر إنشاء.

| المورد       | اصطلاح staging المقترح                | الضابط المطلوب                                         |
| ------------ | ------------------------------------- | ------------------------------------------------------ |
| Worker/Pages | `hala-ai-os-staging`                  | نشر منفصل ومراجعة before/after وrollback معروف         |
| D1           | `halah-staging-d1`                    | بيانات demo فقط، migrations مثبتة، backup وخطة حذف     |
| KV           | `halah-staging-cache`                 | rate limit وOAuth state قصير العمر فقط، بلا مصدر حقيقة |
| Vectorize    | `halah-staging-ar`                    | مرشح retrieval فقط؛ التحقق من D1 قبل أي claim          |
| storage      | bucket staging منفصل عند الحاجة للصور | مفاتيح منظمة، retention، منع public-by-default         |
| أسرار        | secrets جديدة مستقلة                  | لا نسخ من الإنتاج؛ لا Git أو logs أو frontend          |

## تسلسل بناء staging

| الترتيب | العمل                                            | معيار الخروج                                                           |
| ------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| 1       | مراجعة الكود وCI وmigrations محلياً              | `pnpm check` وbuild جاف و`git diff --check` ناجحة                      |
| 2       | اعتماد خطة الموارد والأسماء والمالك والـrollback | موافقة صريحة على provisioning staging فقط                              |
| 3       | إنشاء موارد staging وbindings بلا أسرار إنتاج    | إثبات عزل الموارد ومراجعة config                                       |
| 4       | نشر نسخة staging غير مربوطة بسلة أو واتساب       | smoke tests وhealth وsession وRTL ناجحة                                |
| 5       | إضافة أسرار staging الجديدة خادمياً              | secret scan وredaction وتأكيد عدم تسرب                                 |
| 6       | اختبار OAuth/authorization في متجر demo          | state أحادي الاستخدام، token مشفر، لا token في المتصفح                 |
| 7       | اختبار webhook في متجر demo                      | raw-body signature، idempotency، retry، inbox فقط                      |
| 8       | اختبار سياسات الاسترداد                          | no-consent/suppressed/purchased/budget/template كلّها تمنع الإرسال     |
| 9       | اختبار محتوى المنتجات                            | 20 SKU demo: facts → evidence → draft → preview؛ بلا production export |
| 10      | مراجعة أمنية وتشغيلية                            | go/no-go مكتوب وموافقة محددة للخطوة التالية                            |

توثق سلة استخدام متجر demo لاختبار التطبيق، وتوضح أن تسجيل webhook يتطلب URL صالحاً يستقبل `POST` وصلاحية `webhooks.read_write`.[1] [2] لا يعني ذلك الموافقة على تسجيله الآن.

## مصفوفة اختبارات القبول

| المجال            | الاختبار                                           | النتيجة المقبولة                          |
| ----------------- | -------------------------------------------------- | ----------------------------------------- |
| الهوية            | session revoked/expired/invalid وcookie same-site  | لا وصول للوحة من دون جلسة صالحة           |
| العزل             | منظمة A تحاول قراءة أو اعتماد item لمنظمة B        | 404 أو 403 من دون تسريب وجود السجل        |
| المنتج            | CSV مفقود/JSON غير صالح/SKU مكرر/أكبر من حد الدفعة | تقرير أسباب، لا facts محفوظة عند الفشل    |
| الدليل            | رابط HTTPS بلا اعتماد يدوي                         | `needs_evidence` فقط، لا نموذج ولا draft  |
| الاسترداد         | حدث مشتَرى أو suppressed أو بلا consent            | terminal reason code، لا رسالة            |
| webhook           | توقيع خاطئ أو body مكرر                            | رفض أو idempotent inbox، لا workflow مكرر |
| تكلفة             | cap غير متاح أو قالب غير معتمد                     | لا جدولة ولا تنفيذ                        |
| RTL/accessibility | لوحة عربية وlogical CSS والتنقل باللوحة            | لا كسر في الاتجاه أو labels أو focus      |
| المراقبة          | خطأ مزود أو retry أو فشل token                     | سجل آمن بلا secret ولا body عميل          |

## Rollback وإيقاف الخدمة

يجب أن تتوافر قبل اختبار أي قناة حية آليات توقف واضحة: إيقاف معالجة الاسترداد، إلغاء جدولة المحاولات غير المنفذة، تعطيل الاشتراكات، تحويل الاتصالات إلى `reauthorization_required` عند فشل التفويض، وإخفاء الواجهة التي توحي بالإرسال. لا يحذف rollback سجل التدقيق، ولا يطبع الأسرار أو محتوى العميل في الاستثناءات.

## قرار الدخول إلى Salla demo

لا تبدأ خطوة متجر demo أو إعداد Salla Partners إلا بعد استيفاء بوابات الكود المحلية والحصول على موافقة محددة. التنفيذ الخارجي التالي — عند طلبه صراحةً — سيكون محصوراً في staging ومتجر demo، ويشمل عرضاً مسبقاً للموارد المتأثرة وخطة rollback.
