# جاهزية الانتقال الفعلي إلى `halah.aura.sa`

**تاريخ الفحص:** 2026-09-01  
**نوع الفحص:** قراءة فقط عبر Cloudflare API ومراجعة source المحلي.  
**لم يُنفذ:** إنشاء موارد، تغيير DNS، نشر Worker، تعديل Pages، تشغيل Salla أو WhatsApp أو Google OAuth.

## النتيجة التنفيذية

النطاق `halah.aura.sa` مرتبط حالياً بمشروع Cloudflare Pages باسم `hala-ai-os`، وليس بالمصدر الجديد `mrshsss16-a11y/halah`. المشروع القديم يستخدم قاعدة D1 باسم `halah-tr-db` ومعرّف مختلف، وKV باسم `HALA_CACHE`، وWorkers AI وVectorize. لذلك **لا يجوز ربط Worker الجديد بقاعدة `halah-tr-db`**؛ schema فيها مختلف عن migrations المصدر الجديد وقد يؤدي ذلك إلى كسر الموقع أو خلط بيانات نظامين.

المسار الآمن للنشر الفعلي هو إنشاء Worker إنتاج مستقل للمصدر الجديد، وإنشاء D1 إنتاج مستقل له وتطبيق migrations الخمس عشرة، وإنشاء KV مستقل لمحددات معدل المصادقة، ثم ربط النطاق بالـWorker بعد فحص smoke وrollback. تبقى Pages القديمة كمرجع رجوع إلى أن يثبت Worker الجديد.

## الموارد المؤكدة

| المورد | الحالة الحالية | القرار |
|---|---|---|
| `halah.aura.sa` | CNAME إلى `hala-ai-os.pages.dev`، وPages alias للمشروع القديم | لا يُعدل قبل اكتمال Worker والنشر المؤكد |
| Pages `hala-ai-os` | إنتاج قائم، يستخدم `halah-tr-db` و`HALA_CACHE` وAI وVectorize | يبقى intact كـrollback؛ لا يُستبدل عبر push |
| D1 `halah-tr-db` | قاعدة legacy فيها 35 جدولاً وview واحداً، وليست schema المصدر الجديد | ممنوع الربط بها |
| D1 `halah-saas-staging` | موجودة وبها جدول migrations فقط تقريباً، ولم تُستخدم للتشغيل الحي | لا تُحوّل إلى production بالاسم فقط |
| KV `HALA_SAAS_STAGING_AUTH_RATE_LIMIT` | موجودة لبيئة staging | لا تُستخدم للإنتاج |
| KV `HALA_CACHE` | مرتبط بالمشروع القديم | لا يُعاد استخدامه لـWorker الجديد |
| migrations المصدر الجديد | 15 migration من `0001_core.sql` إلى `0015_recovery_policy_versioning.sql` | تُطبق على D1 إنتاج جديد فقط |

## الأسرار

أظهر فحص إعدادات Pages القديمة أسماء أسرار تكاملية، لكن القيم غير متاحة للفحص. لا يمكن اعتبارها أسراراً صالحة للمصدر الجديد ولا يجوز نسخها. Worker الجديد يحتاج أسراراً مستقلة تُدخل عبر Secret bindings بعد تحديد التدفقات المطلوبة. لا يُفعل Salla أو Google أو WhatsApp في الإنتاج ضمن نشر الواجهة والبنية الأول.

## ما تم نقله إلى المصدر الجديد

أضيفت مصفوفة فجوات للمشروع الأساسي، ورحلة onboarding عربية RTL، وصفحة اتصالات تعرض Salla 1-Click كمحاكاة محلية فقط في development. اجتازت التغييرات 100 اختبار وحدة/عقد، و27 اختبار integration، وtypecheck وlint وbuild dry-run، مع إصلاح تنسيق وثيقة الفجوات.

## قرار القبول قبل الإنشاء والنشر

قبل العملية الفعلية يلزم تأكيد محدد لإنشاء D1 إنتاج جديد وKV إنتاج جديد وإنشاء Worker إنتاج مستقل، ثم تطبيق migrations، ثم ربط `halah.aura.sa` بالـWorker. إذا لم تُنشأ هذه الموارد، فإن نشر المصدر الجديد على Pages القديم أو ربطه بـD1 legacy ليس نشرًا آمناً ولا مقبولاً.

## خطة rollback

يبقى Pages `hala-ai-os` وD1 `halah-tr-db` دون حذف أو تعديل. إذا فشل smoke بعد ربط النطاق، يُعاد توجيه النطاق إلى Pages القديم أو يُفصل route الجديد وفق إعداد الربط الذي سيُنفذ بعد الموافقة. لا تُحذف الموارد الجديدة حتى يثبت الاستقرار وتُحفظ سجلات النشر.
