# خطة: العزل + الذاكرة + استرداد السلة + مكتبة ردود الدعم

**التاريخ:** 2026-09-05
**المصدر:** فحص فعلي لكود `hala-ai-os` الحي + مراجعة `hala-project` (المشروع الموازي، 2026-09-04)
**القاعدة:** كل بند أدناه متحقَّق منه بالكود بسطر ورقم — لا افتراضات.

---

## 0. الحكم على المشروع الموازي (`hala-project`)

المشروع الموازي **أفضل هندسياً** (TypeScript، monorepo، عزل منظمات، RBAC، خزانة رموز مشفرة،
بوابة أدلة ضد الهلوسة، ١٢٧ اختبار) لكن **سلة وواتساب وGoogle فيه كلها mock** — صفر اتصال حي،
والكاتب نفسه يقرّها بمصفوفته.

مشروعنا الحي عكسه: التكاملات الحقيقية شغالة بعد أسابيع تصحيح فعلي (سلسلة B4 السبعة، تعدد
مستأجري واتساب، B3 بالجملة).

**القرار:** لا ننفّذ خطة النقل/الـcutover المقترحة بذاك الملف (Worker جديد + D1 جديد + تحويل
نطاق) — تعيد بناء أشهر شغل حقيقي مقابل بنية أنظف بلا تكاملات. **نسحب منه الأفكار المحدّدة
ونطبّقها داخل بنيتنا الحالية.** هذه الخطة هي ذلك السحب.

المتجر أ حرفياً** بسياسته وأوقاته واسمه.

**أثر التسريب ٢ عملياً:** عميل سعودي يتسوّق من متجرين كلاهما على هالة → بوت المتجر ب يحمّل
`last_product` و`chat_summary` من محادثة المتجر أ ويبني رده عليها.

## 2. المراحل

### ✅ P0 — إغلاق التسريبين — **تم** (2026-09-05، `250e54d`)

1. **مفتاح الكاش:** `merchantId` إلزامي (لا افتراضي `"global"` بأي مسار متعدد المستأجرين)
   + بصمة كاملة (hash) للـsystem prompt بدل أول ٢٠ حرف + `skipCache` لأي رد فيه بيانات عميل.
2. **الجلسة:** `getOmnichannelSession` تطلب `merchantId` إلزامياً بمسار الهاتف، وتحديث
   المستدعيين بالويبهوك.
3. **اختبار عزل آلي** يُضاف لـ`tests/api.test.mjs`: متجران، نفس السؤال، نفس رقم العميل
   → لا مفتاح كاش مشترك ولا جلسة مشتركة. يفشل الاختبار لو رجع أحد يكسر العزل لاحقاً.

**التحقق الفعلي:**
- أُثبت التسريب أولاً بمحاكاة للمفتاح القديم: متجران مختلفان → **مفتاح متطابق حرفياً**
  (`ai_cache:global:أنتِ_مساعدة_متجر_سعو:وش_سياسة_الإرجاع_عندكم؟`).
- ٧ اختبارات عزل أُضيفت لـ`tests/api.test.mjs` تعيد إنتاج العطلين — **33/33 تمر**.
- نشر حي + فحص KV بعد استدعاء فعلي: المفتاح المكتوب على الإنتاج الآن
  `ai_cache:v2:hala:<sha256>` — الصيغة المعزولة الجديدة.
- الكاش القديم كان فاضياً وقت الإصلاح (TTL قصيرة + حركة قليلة) — لا مفاتيح ملوّثة باقية.

### 🟠 P1 — ذاكرة العميل طويلة الأمد (migration جديدة)

الفكرة المسحوبة من `TENANT_SCOPED_RAG_AND_CUSTOMER_MEMORY.md`، مبسّطة لبنيتنا:

- `customer_profiles`: `merchant_id + phone_hash` (مفتاح مركّب — العزل من التصميم لا من
  الاستعلام)، الحالة، الموافقة، تاريخ آخر تفاعل.
- `customer_memory_facts`: **تفضيلات صريحة فقط** (قالها العميل بنفسه)، مع نص المصدر وتاريخه.
  الاستنتاجات لا تُحفظ ولا تُستخدم بقرار حساس بلا تأكيد.
- استرجاع الذاكرة **بعد** تحديد المتجر من القناة الموثقة (`phone_number_id`) — **لا** من نص
  العميل، ولا من الهاتف وحده.
- حذف/سحب موافقة: كلمة واحدة من العميل تُلغي الحقائق وتمنع تحميلها مستقبلاً.

**معيار القبول:** عميل يعود بعد يومين لنفس المتجر → يُكمل السياق. نفس العميل يكلّم متجراً
ثانياً → يبدأ من صفر. طلب حذف → لا تُحمَّل أي حقيقة بعده.

### 🟠 P2 — استرداد السلة المتروكة الحي (يغلق البند ٣ و٤)

آلة حالة صريحة، مسحوبة من المشروع الموازي:

```
received → deduplicated → policy_checked → eligible → scheduled → sent | suppressed | failed
```

- **لا استدعاء LLM ولا واتساب داخل معالج الويبهوك** — الويبهوك يستقبل ويحفظ فقط، والمعالجة
  بالخلفية عبر `cron-worker` الموجود (نفس نمط `bulk_process.js` اللي بنيناه بـB3).
- **idempotency** على معرّف السلة: حدث مكرر ≠ رسالة ثانية.
- حراس إلزامية: نافذة واتساب ٢٤ ساعة، حد محاولات، قائمة إيقاف (opt-out)، حصة الرسائل الشهرية
  (`message` bucket الموجود)، ومفتاح إيقاف للتاجر.

**🔑 قرار مطلوب منك — التخفيضات:**
قاعدة الصدق بالمشروع تمنع اختراع سعر أو خصم. الخياران المقبولان:
- **(أ) الأسهل والأأمن:** التاجر ينشئ كوبوناً بلوحة سلة ويلصق رمزه بالداشبورد → هالة ترسله كما
  هو. (بلا اعتماد على API إضافي، ينفّذ فوراً)
- **(ب) الأقوى:** هالة تولّد كوبوناً حقيقياً عبر Salla Coupons API لكل سلة.
  ⚠️ **يحتاج تحققاً من توثيق سلة الحي أولاً** — لا يوجد بمهارة `salla-integration` عندنا أي
  توثيق لهذا الـendpoint أو صلاحياته، فلا أعِد به قبل التحقق.

**معيار القبول:** حدث سلة مكرر لا ينتج رسالتين. سلة لمتجر غير متصل لا تُعالج. عميل موقوف لا
يُرسل له. الرسالة ما تذكر خصماً إلا لو له مصدر حقيقي.

### 🟡 P3 — مكتبة ردود الدعم + الردود الجاهزة من لحظة الربط

**(أ) مكتبة أسلوب الدعم** — نفس آلية مكتبة أوصاف المنتجات المبنية أصلاً، بمخزن منفصل:
- صيغة CSV: `السؤال,الرد_الفعلي,النوع` (شحن/إرجاع/اعتراض سعر/تردد شراء…)
- تُستخدم لمعايرة **النبرة والبنية فقط** — ممنوع نقل أي حقيقة (سياسة/سعر/مدة) لمتجر آخر،
  نفس الحاجز المطبَّق بمكتبة الأوصاف.
- ملف الكليشات الممنوعة: عبارات آلية نمنعها صراحة بالبرومبت.

**(ب) ردود جاهزة تُبنى لحظة ربط المتجر** — يغلق البند ٥ (`merchant_faqs` الفاضي):
عند نجاح ربط سلة، تُشغَّل مهمة خلفية تسحب منتجات المتجر وبياناته وتولّد مسبقاً أشهر ٢٠–٣٠
سؤالاً وردودها → تُحفظ بـ`merchant_faqs` → تُفهرس بـVectorize بنطاق المتجر.
النتيجة: التاجر يربط متجره ويلقى بوته يعرف يرد **من أول دقيقة**، بلا إدخال يدوي.

**حارس إلزامي:** أي رد يعتمد على سياسة/سعر/مدة لازم يرجع لمصدر فعّال بـD1، وإلا يقول «أحتاج
أتأكد» أو يصعّد للتاجر — **بوابة الأدلة**، أهم فكرة بالمشروع الموازي.

## 4. ما لن نفعله (حدود صريحة)

- لا نقل/cutover للمشروع الموازي، ولا استبدال Pages بـWorker جديد.
- لا اختراع خصم أو سعر أو نسبة — قاعدة الصدق بـ`CLAUDE.md`.
- لا استدعاء LLM أو إرسال واتساب داخل معالج ويبهوك.
- لا استيراد رسائل عملاء خام لمكتبة الأسلوب تلقائياً (تنقية واعتماد يدوي أولاً).
- لا ذاكرة تُحمَّل بهوية غير موثقة (تشابه اسم أو رقم مكتوب بالرسالة لا يكفي).
