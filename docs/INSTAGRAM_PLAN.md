# المرحلة ١ — المحوّل والويبهوك (أنا) · ٣-٤ أيام

## ١.١ `functions/_lib/integrations/instagram.js`

يحقق عقد المحوّل (`PARALLEL_TRACKS.md` §أ.٣) بالحرف. المرجع البنيوي: `whatsapp.js`.

```js
export function isConfigured(env, conn)      // conn.ig_user_id && conn.access_token
export async function receive(request, env)  // توقيع → أحداث موحّدة
export async function send(env, to, payload) // رد علني / خاص / رسالة مباشرة
export async function fetchContext(env, id)  // سياق المنشور (اختياري)
```

**`verifyIgSignature`** — نسخة من `verifyWaSignature()` (`whatsapp.js:37`) بسر
`INSTAGRAM_APP_SECRET`: مقارنة ثابتة الزمن، و`if (!appSecret) return false` (S1، fail closed).
🔴 **السر الموقِّع = App Secret، لا Verify Token.**

**المُحلِّل — ثلاثة فخاخ إلزامية:**

| الفخ | المعالجة |
|---|---|
| شكل الحمولة يختلف بين المسارين | Instagram Login: `entry[].field` + `entry[].value` مباشرة (المعرّف `value.id`). Facebook Login: `entry[].changes[]` (المعرّف `comment_id`). **نحلّل الشكلين دفاعياً** — أمثلة الإنترنت أغلبها للمسار الثاني وتقرأ `undefined` صامتاً |
| `is_echo: true` | رسالة أرسلها حسابنا نفسه ⇒ **تُتجاهل فوراً**. بدونها حلقة رد ذاتية لا نهائية تحرق الحصة |
| التكرار مضمون | إعادة محاولة Meta على مدى ٣٦ ساعة + دفعات حتى ١٠٠٠ ⇒ **إزالة تكرار بـ`value.id` / `message.mid`** |

## ١.٢ `functions/api/instagram/webhook.js`

- `onRequestGet` — تحقق `hub.verify_token` ⇒ إعادة `hub.challenge` نصاً خاماً، وإلا **403**
- `onRequestPost` — توقيع ⇒ تحليل ⇒ ربط تاجر ⇒ حصة ⇒ توليد ⇒ **طابور مراجعة**
- **ردّ `200` دائماً** بعد قبول الحمولة (شرط Meta)، والمعالجة الثقيلة بعده

## ١.٣ العزل — `entry[].id` هو المفتاح

`entry[].id` = `<IG_ID>` لحساب التاجر. **هذا وحده يربط الحدث بالتاجر**، تماماً كما
`phone_number_id` بواتساب — والتعليق بـ`whatsapp.js:147` يوثّق العطل الذي نتج من إسقاطه
(كل الرسائل نُسبت لتاجر واحد مثبّت). **لا نكرره.**

**هجرة `0017_ig_connections.sql`:**
```sql
CREATE TABLE IF NOT EXISTS ig_connections (
  merchant_id TEXT NOT NULL,
  ig_user_id TEXT NOT NULL UNIQUE,   -- entry[].id — مفتاح ربط الويبهوك
  username TEXT,
  access_token TEXT NOT NULL,        -- long-lived، ٦٠ يوماً
  token_expires_at INTEGER NOT NULL,
  created_at TEXT DEFAULT (datetime('now')),
  PRIMARY KEY (merchant_id, ig_user_id)
);
CREATE INDEX IF NOT EXISTS idx_ig_conn_user ON ig_connections (ig_user_id);
```

⛔ **لا نثق بأي هوية بالحمولة عدا `entry[].id` بعد التحقق من التوقيع.**

# المرحلة ٢ — الشخصية والنشر عبر المراجعة (أنا) · ٣-٤ أيام

## ٢.١ الشخصية — مصدر واحد، سياق قناة

`persona.js` يبقى المصدر الوحيد (M2). يُضاف تصدير لسياق إنستغرام — **لا نسخة ثانية من الشخصية**:

| القناة | النبرة | قيود إضافية |
|---|---|---|
| تعليق علني | تسويقية، مختصرة، دافئة — يشوفها الجمهور | **صفر رقم سعر** · صفر تفاصيل عميل · صفر وعد غير مؤكد |
| رسالة خاصة | شخصية، مفصّلة أكثر — محادثة فردية | نفس قواعد واتساب |

🔴 **خطر خاص بالعلني:** رقم سعر خاطئ بتعليق **علني ودائم** يُلتقط بلقطة شاشة. القاعدة
القائمة ("ممنوع ذكر أي رقم سعر — توجّه للاستشارة") تنطبق هنا بحدّة مضاعفة.

**الإفصاح عن الأتمتة — إلزام قانوني** (سياسة Meta، كاليفورنيا وألمانيا صراحةً):
أول رد بأي خيط يفصح أنه آلي. منسجم مع قاعدة الصدق بـ`CLAUDE.md` — لا تعارض.

## ٢.٢ 🔴 كل رد يمرّ ببوابة المراجعة — صفر نشر آلي

```js
await enqueue(env, {
  merchantId,
  kind: "social_reply",                 // موجود بـREVIEW_KINDS
  payload: { channel: "instagram", commentId, igId, draft, sourceText, expiresAt }
});
```

`reviewQueue.js` مبني ومُهاجَر (`0016_review_queue.sql`) بعزل صارم. **الناقص: النشر عند
الاعتماد** — `approve()` اليوم يغيّر الحالة فقط ولا يرسل شيئاً.

**يُبنى: `functions/_lib/services/publishApproved.js`**
- يُستدعى بعد `approve()` من `admin/review.js`
- يقرأ `payload.channel` ⇒ يوجّه لمحوّل القناة
- يسجّل نتيجة الإرسال (نجاح/فشل) على الصف نفسه
- فشل الإرسال **لا يقلب** الحالة لـ`pending` — يُعلَّم `approved` + خطأ إرسال، ويُعاد يدوياً

## ٢.٣ ⏳ النوافذ الزمنية — تعارض حقيقي مع المراجعة البشرية

| النوع | النافذة | الأثر |
|---|---|---|
| رد علني على تعليق | لا حد موثّق | آمن |
| Private Reply | **٧ أيام** من التعليق · **مرة واحدة فقط** لكل معلّق | مؤقّت إلزامي |
| رسالة مباشرة | **٢٤ ساعة** من رسالة العميل | مؤقّت إلزامي |
| تعليق بث مباشر | **مدة البث فقط** | ⛔ **الرد الآلي عليه مستحيل مع بوابة بشرية — نقبله صراحةً، لا نبني استثناء** |

**المطلوب بلوحة المراجعة:** حقل `expires_at` بالحمولة، إبراز ما يقترب من الانتهاء،
ووسم "فات الأوان" لما انتهت نافذته — بدل محاولة إرسال ستفشل.

## ٢.٤ حدود المعدل — طابور لكل تاجر

| الحد | القيمة |
|---|---|
| تعليقات/وسائط (BUC) | `4800 × Impressions` بـ٢٤ ساعة — 🔴 **حساب خامل ⇒ Impressions≈0 ⇒ سقف≈صفر** |
| Private Reply (منشورات) | ٧٥٠/ساعة |
| Send API (نص) | **١٠٠/ثانية** (التوثيق يتعارض ١٠٠ مقابل ٣٠٠ — نأخذ الأدنى) |
| سقف الصمت الكلي | **٧٢٬٠٠٠ رسالة** ⇒ الحساب كله يتوقف |

**الأثر:** طابور إرسال **لكل `merchant_id` على حدة**. تاجر كثيف لا يستهلك حصة الباقين —
نفس درس سلة (طلب/ثانية). والاعتماد على الويبهوك بدل استطلاع `/comments` (توصية Meta الصريحة
لتفادي BUC).

# المرحلة ٣ — الذاكرة عبر القنوات (قرار مطلوب) · ٢ يوم

## ما يعمل تلقائياً اليوم

**معرفة المتجر** — Vectorize بمفتاح `storeId`. نفس الجواب على إنستغرام وواتساب والموقع،
بلا أي عمل إضافي. **متسق أصلاً.**

## ما لا يعمل — والسبب بنيوي لا نقص تنفيذ

سجل محادثة **العميل نفسه** مربوط بـ**رقم الجوال** بواتساب (`recentWaHistory`).
إنستغرام يعرّفه بـ**IGSID** — معرّف مختلف كلياً، **بلا أي رابط طبيعي برقم الجوال**.

> البوت لا يستطيع معرفة أن "أحمد بإنستغرام" هو "٠٥xxxxxxxx بواتساب" — **إلا إن قال العميل ذلك بنفسه**.
> هذا حد تقني حقيقي، لا خيار تصميمي.

## الحل المقترح — جسر هوية صريح

```sql
CREATE TABLE IF NOT EXISTS customer_identities (
  merchant_id TEXT NOT NULL,
  channel TEXT NOT NULL,          -- 'instagram' | 'whatsapp'
  channel_user_id TEXT NOT NULL,  -- IGSID أو رقم الجوال
  linked_key TEXT NOT NULL,       -- المفتاح الموحّد للعميل عبر القنوات
  linked_at TEXT DEFAULT (datetime('now')),
  PRIMARY KEY (merchant_id, channel, channel_user_id)
);
```

**متى يُربط:** حين يذكر العميل رقمه بمحادثة إنستغرام، أو ينتقل عبر رابط تحويل يحمل رمزاً
قصير العمر. من تلك اللحظة، السياق ينتقل بين القناتين.

**بلا هذا الربط الصريح: صفر استمرارية.** نقولها للتاجر بوضوح بدل الإيحاء بخلافها.

⚠️ **بُعد خصوصية:** ربط هويات عميل عبر منصتين بيانات شخصية. يُربط **بموافقة ضمنية من فعل
العميل نفسه** (ذكر رقمه / ضغط رابط التحويل)، لا بمطابقة صامتة بالاسم أو أي استدلال.

**قرارك المطلوب:** يُبنى الآن ضمن المرحلة ٣، أم يؤجَّل حتى أول عميل يحتاج الانتقال فعلياً؟
(توصيتي: **يؤجَّل** — لا نبني ميزة قبل طلب حقيقي، والقاعدة موثّقة بـROADMAP C7 لحالة مشابهة.)

# المرحلة ٤ — التوكن والاستمرارية (أنا) · ١ يوم

## ٤.١ تدفق الربط

```
/api/instagram/install  → https://www.instagram.com/oauth/authorize?...&state=<موقّع>
/api/instagram/callback → code → short-lived → long-lived (٦٠ يوم) → ig_connections
```

⚠️ **`state` غير مذكور بتوثيق Meta لهذا التدفق — نضعه رغم ذلك** عبر
`core/oauthState.js` تماماً كتدفق سلة. **لا نُضعف قاعدة أمن لأن المزوّد لم يطلبها.**
و`redirect_uri` يجب أن يطابق حرفياً عند تبديل الـcode وإلا يُرفض.

## ٤.٢ 🔴 cron التجديد — بلاه سقوط صامت بعد ٦٠ يوماً

نفس درس توكن واتساب المؤقت الذي أوقف البوت ٤٥ يوماً. يُضاف لـ`cron-worker` القائم:
- يجدّد كل توكن يتبقى له < ١٠ أيام (`GET /refresh_access_token?grant_type=ig_refresh_token`)
- ⚠️ **يُرفض التجديد قبل مرور ٢٤ ساعة على الإصدار** — لا نجدّد فور الإنشاء
- فشل التجديد ⇒ تنبيه واتساب للأدمن (مسار `healthcheck` القائم)

## ٤.٣ الاشتراك بالحقول — خطوتان، نسيان الثانية عطل شائع

1. اشتراك التطبيق بالحقول من لوحة التطبيق (`comments`, `messages`)
2. **تفعيل حساب التاجر بنداء API** — يُنفَّذ آلياً بنهاية الـcallback:
```
POST /<IG_ID>/subscribed_apps?subscribed_fields=comments,messages
```
